Revealing accessibility gaps in user behavior

A Hotjar feature that turns behavior data into accessibility insight: where specific user groups struggle, so teams can make more inclusive decisions.

Hotjar sees behavior. It doesn't see who is being left behind.

Hotjar records how people use a website through heatmaps, session recordings and feedback. It doesn't show whether an interface is failing specific groups. This project adds that layer, reading accessibility gaps out of behavior Hotjar already captures.

Team: Shani Leibner, Omer Barak, Hila Lustig and Shahar Liz Ben Or.

The problem

When interfaces ignore differences in ability, culture or digital literacy, they create unequal access. Those gaps rarely show up as bugs, so nobody goes looking for them.

The solution: an Accessibility Issues page

A single page that lists where specific user groups struggle, ranked by how far they deviate from the average, with each issue linking straight into the heatmap or session replay that shows it.

Research: cultural gaps don't show up as bugs

We worked in three threads:

  • Reading the signals. Which behavioral patterns actually point to a gap, and how to communicate them.
  • Existing patterns. How teams already explore data in Hotjar, which turned out to be mostly through tables.
  • Interviews. Product managers and analysts on how they detect, interpret and prioritize issues today.

That gave us three rules: build on tools Hotjar users already know, organize gaps by user population, and measure every pattern against the overall average so deviation becomes the signal.

Who uses it

Product manager

Needs to see which segments have issues so fixes can be prioritized by impact.

Business analyst

Needs behavioral patterns across segments that reliably point to a gap, and a way to turn them into insight.

The shared job: find accessibility issues across the site, understand their real impact, and confirm them through heatmaps and recordings.

Iterations

Where the feature lives

First try
A standalone tab with alerts.
Problem
It clashed with Hotjar's language and navigation.
Change
Folded into Hotjar's existing patterns.

Showing who is affected

First try
Kept demographic data to a minimum.
Problem
Issues read as incomplete and unclear.
Change
Made the affected group the point of each row.

How much the table shows

First try
A stripped-down table, heatmap behind a button.
Problem
Essential details were missing.
Change
Just enough context to grasp the issue, still scannable.

Framing the problem

First try
One headline with a time range and user type.
Problem
It hid which segments were affected.
Change
Sub-topics that name the segments.

What's next

Built into an analytics tool, accessibility stops being a separate audit and becomes part of everyday product decisions. Today the feature finds gaps through behavior. The next step is estimating their business cost in conversion and revenue, and later, recommending fixes.
